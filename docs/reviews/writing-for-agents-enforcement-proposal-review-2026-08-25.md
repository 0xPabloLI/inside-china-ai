# `writing-for-agents` 规则执行率改善方案：审核报告

**审核对象**：`docs/research/writing-for-agents-enforcement-proposal.md`  
**审核结论**：**有条件通过；在实施前须完成以下高优先级修订。**  
**审核范围**：方案的因果链、规则一致性、触发边界、流程覆盖、可验证性，以及所引用文件的完整性。未修改仓库文件。

## 执行摘要

方案选择“**分层触发 + 行动路径中的指针**”是正确方向。现有技能明确指出：上下文指针的措辞决定材料何时、以多可靠的方式被加载；将触发条件放在实际执行分支上，因而有合理的机制基础。[1] 但当前版本还不能直接落地：它会与 `DOCS-INDEX.md` 的无条件规则产生直接矛盾，且只给 Step 4 加指针，没有覆盖创建 spec、ticket、研究文档，以及 Step 8 文档同步这些主要文档操作路径。

更关键的是，“小改”把**链接修复、状态更新**一概列为豁免项，忽略了链接、索引和指针本身会改变 Agent 是否能到达某个规则或如何到达它。对 Agent 文档而言，这类改动不能仅按行数或表面形态归为低风险。建议以“是否改变信息结构、权威来源、执行行为或上下文指针”为判定核心，并在不确定时默认加载 skill。

| 维度 | 评价 | 结论 |
|---|---|---|
| 问题方向 | 合理 | 保留“降低无收益加载、强化触发”的目标 |
| 根因证据 | 不足 | 机制解释成立，但“频繁被跳过”和执行率改善均缺少基线与验证设计 |
| 规则一致性 | 不通过 | 拟改 `AGENTS.md` 与现行 `DOCS-INDEX.md` 直接冲突 |
| 流程覆盖 | 不通过 | 指针只覆盖 Step 4，漏掉 Step 1–3、Step 8 的文档生产路径 |
| 判定边界 | 不通过 | “小改”定义语义不充分，尤其错误豁免指针/索引变更 |
| 可验证性 | 不通过 | 缺少行为场景、验收标准、试运行与回滚规则 |

## 必须修订的问题

### 1. 规则将出现跨文件矛盾，违反单一事实来源

拟议的 `AGENTS.md` 条目允许部分小改免于加载 skill；但现行 `docs/DOCS-INDEX.md` 的 Layer Placement Rules 明确规定“修改 `docs/` 下任何文档前”都要加载该 skill。[2] 若只按方案修改 `AGENTS.md`，Agent 会同时读到两个相互冲突的命令：一个允许豁免，另一个不允许。

> **建议裁决**：将“是否需要加载 skill”的规范性定义只保留在 `AGENTS.md`；把 `DOCS-INDEX.md` 第 20 行改为指向该条目，而不再重复“任何修改均加载”的规则。这样 `DOCS-INDEX.md` 只保留 Layer Placement 的操作检查，避免双重权威来源。

此处也暴露出原文中的分类冲突：`AGENTS.md` 使用“`docs/research/` 下的执行文档”，而 `DOCS-INDEX.md` 定义 `docs/research/` 为 L2，并要求 L2 不放执行指令。[2] 修订时应把该表述替换为“`docs/` 下会被 Agent 执行流程读取或由上下文指针到达的文档”；不要把 L2 研究文档称作“执行文档”。

### 2. Step 4 单点指针不能解决方案自己定义的根因

方案认为问题是规则不在 Agent 的行动路径上，但只拟在 Step 4 追加指针。现行工作流在 Step 1 形成分析材料、Step 2 生成 spec、Step 3 生成 ticket，而 Step 8 又明确要求同步更新及归档文档。[3] 其中 Step 2、3 的产物正是拟议规则明确覆盖的 Agent 消费文档。仅覆盖 Step 4 会保留大部分“创建新文档”路径上的原问题。

**建议改为统一的“文档改动门槛（docs-change gate）”。** 将其放在工作流步骤列表之前，或紧邻 Step 1–4 与 Step 8 的共同入口，并让上述步骤使用同一个短语引用它。该门槛必须前置触发词，例如“**在创建或改动 `docs/` 前**”，而非事后式的“如需修改”。这比 Step 4 尾部一条很长的补充更符合技能对指针“前置触发、分支清楚”的要求。[1]

### 3. “大改/小改”应按语义风险，而不是表面改动类型

当前例子把“链接修复”作为可豁免小改，风险过高。普通外链或拼写链接的修复可以低风险；但改变一个 `AGENTS.md` 指针、`DOCS-INDEX.md` 索引项、Skill 名称，或链接目标文件，会改变 Agent 可达信息，属于语义性改动。现行 skill 把指针视为决定 Agent 何时加载材料的对象，因此该类改动应强制加载。[1]

建议将“豁免”写成必须**同时**满足的封闭条件，而不是给出开放式示例：

| 规则类别 | 处理 | 判定条件 |
|---|---|---|
| 强制加载 | 编辑前加载 skill | 创建、删除、移动或重命名文档；改 `AGENTS.md`；新增/删除/合并/拆分章节；新增或修改规则、前置条件、例外、完成标准、执行步骤；新增、删除或重定向 Agent 上下文指针；改 `DOCS-INDEX.md` 的目录、分层或指针语义 |
| 可豁免 | 无需加载，但必须保持原有结构与权威来源 | 仅更正拼写、格式、事实值、失效的非 Agent 指针链接，或仅更新不会改变流程含义的状态标记；不改变标题层级、文件位置、引用关系、规则语义和操作步骤 |
| 不确定 | 按强制加载处理 | 无法明确证明该变更符合“可豁免”的全部条件 |

这里不建议采用行数阈值。“一行”可以新增高影响的前置条件或改写一个指针；“多行”也可能只是同一张表的事实校正。语义边界更稳定，也更可审查。

### 4. “豁免但仍遵循三原则”的指令不够可执行

对错别字或纯事实值修正要求“仍遵循 SSoT、渐进披露、无重复”，容易成为没有完成标准的泛化提醒。应把它改成可判断的保持性约束：

> **建议替换**：豁免变更不得改变文档的信息层级、规则的唯一权威来源、或现有指针关系；如变更会新增、迁移或重复规则，转入强制加载路径。

这既保留三原则的意图，又避免要求 Agent 在无需结构设计的改动中重复进行完整的文档架构审查。

### 5. 预期效果不可测量，且“软约束无解”的论证过强

“在操作路径上增加指针”是可检验的干预，而“若 Agent 连三原则都跳过，加载 skill 也会被跳过”只是可能情况，不能据此得出方案已触及软约束上限。技能文本恰恰表明指针措辞会影响触发可靠性。[1] 因此该干预值得试验，但应将其描述为**待验证的假设**，而不是既定效果。

方案需补充一个最小验证计划：选取至少 8 个覆盖下表的模拟或真实文档改动，记录是否在编辑前走到正确分支、是否错误加载、以及是否漏加载。验收标准建议为：所有强制场景均加载；所有豁免场景均保持信息结构不变；不确定场景均升级为加载。若连续两轮出现漏加载，则回滚豁免范围，优先收紧“链接/索引/状态”类别。

| 场景 | 预期分支 | 关键验收点 |
|---|---|---|
| 新建 `docs/research/` 文档 | 强制加载 | 创建前加载，明确其 L2 定位 |
| 新建 spec 或 ticket | 强制加载 | Step 2/3 路径被门槛覆盖 |
| Step 4 改执行步骤或完成标准 | 强制加载 | 文档语义改动不会被“顺手修改”绕过 |
| Step 8 归档并更新目录索引 | 强制加载 | 索引和可达性改动被识别 |
| 修正文档中的拼写 | 豁免 | 无结构、规则、指针变化 |
| 修复普通资料链接 | 豁免 | 链接不是 Agent 上下文指针 |
| 将 `AGENTS.md` 指针换到新文档 | 强制加载 | 不能被“链接修复”误分类 |
| 无法判定某条状态更新是否影响流程 | 强制加载 | 默认安全分支生效 |

## 方案文档本身还应补齐的交付项

根据现行项目流程，修改既有文件必须有 Modified Files Impact，且场景矩阵应形成可验证的行为用例。[3] 因此提案应新增：影响文件清单（至少 `AGENTS.md` 与 `docs/DOCS-INDEX.md`）、各文件的规则消费者、上述八类行为场景、验证方式、回滚条件，以及“无代码/无 hook 改动”的明确边界。当前“预期效果”和“风险”章节可以保留，但应被这些可验收内容支撑。

对于“CatPaw 没有文件编辑前 hook、技术上不可行”的断言，当前材料只显示它被视为待讨论问题，并未提供实现或平台能力证据。[4] 在没有独立验证前，应采用上文的中性表述，不能将其作为排除备选方案的事实前提。

## 最终裁决

建议**批准方案方向，不批准当前文本直接实施**。完成以下四项后即可进入实施流程：统一 `AGENTS.md` 与 `DOCS-INDEX.md` 的权威关系；把 Step 4 单点提醒升级为覆盖 Step 1–4 和 Step 8 的前置门槛；以语义风险重写豁免边界并保留“无法判定即加载”；加入场景矩阵、验收指标、回滚规则和影响评估。这样既能降低无价值的加载，又不会把决定 Agent 行为的规则、索引与指针误放入“小改”通道。
