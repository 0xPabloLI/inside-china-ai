# TTS 冷启依赖复用：预装 site-packages 数据集（2026-11-23，`#1520`）

> **上游票**：`#1512`（冷批四段取证：内核 405 s 中依赖安装 211–309 s）、`#1515`（重试降到 63.9–71.5 s，冷启仍 351 s）。
> **下游票**：无下游：本票把冷启的固定安装段去掉；后续只有「数据集重建」维护动作，不改变产出。

`#1512` 的结论是冷跑墙钟 1023 s 里 Kaggle 内核只有 405 s，而内核里 78% 是重新 `pip install` 3.7 GB wheelhouse；`#1515` 解决了重试，首跑仍付这 211–309 s。本报告回答 `#1520` 的验收：把冻结 wheelhouse 预装成可挂载数据集后，**真实冷启降到多少、挂载形态是什么、失败时能否无痛回落**。所有运行数字来自 2026-11-23 的真实 Kaggle 内核，不是本地模拟。

## 结论

预装数据集把 3.7 GB wheelhouse 的安装段从真实冷启路径移除了。2026-11-24 同一 harness 的 2 包 / 4 scene 冷批：fast path `engineWallMs=247.6 s`，wheelhouse 基线 `374.8 s`，省 **127.2 s（33.9%）**；内核内部 173.3 s vs 298.0 s，省 **124.7 s（41.8%）**；依赖安装从 185.5 s 降到 0，4/4 wav 的 SHA-256 与基线逐字节一致。但票面 `<120 s` **没有达成**：剩余 247.6 s 里，归档解包 49.6 s、模型加载 32.8 s、四段合成 32.4 s，另有约 74 s 的队列/下载/宿主开销；只砍安装段无法把端到端压到 120 s。该结果把「依赖安装 211–309 s」这个原始问题解决了，但把票面目标改写成 247.6 s 是产品口径变更，不能由实现单方面宣布。

## 构建

构建走一条**不复制 pin**的路径：`push-site-packages-build.sh` 把仓库里的 `cosyvoice3_cuda_kernel.py`、`build-site-packages-dataset.sh`、`wheelhouse-manifest.json` 一起 base64 嵌进一个 CPU carrier kernel；carrier 只负责落盘并执行构建脚本。安装块仍是生产内核那一段，所以构建出来的版本与生产 `pip install` 解析的是同一份 wheelhouse 和同一组 pin，不存在第二份清单漂移。

- 构建模式由 `COSYVOICE3_SITE_PACKAGES_TARGET` 打开：内核装完依赖、写完 `site-packages-dists.json` 就 `sys.exit(0)`，**早于 CosyVoice clone 和模型加载**。
- 安装进一个 venv（`python3 -m venv --without-pip --copies`），再用镜像自带的 `pip` 引导；`pip` 因此只看见 venv 里已装的包，后续 pin 需要降级时不会被静默跳过。Kaggle 镜像的 `ensurepip` 直接失败（v2 的 ERROR 就是它），`--without-pip` + 复制 pip 是这台镜像上唯一可用的组合。
- 自足性由构建脚本独立证明：`python3 -S` 子进程只把目标目录放进 `sys.path`，导入 `torch / onnxruntime / diffusers / huggingface_hub / numba / librosa`，并检查每个 `__file__` 都在目标目录内。`python -S` 看不到镜像 site-packages，所以这一步能识破「只是借了镜像的 torch」的假成功。

本次构建的实测：

| 项 | 值 | 依据 |
| --- | --- | --- |
| 构建内核墙钟 | 258 s | 日志最后一条 `build-site-packages-dataset.sh exit: 0` 的时间 |
| 目标目录 | 6,924,052,686 B | `target is … bytes; packing one tar.zst` |
| 发布归档 | 2,879,940,507 B（`tar.zst`，level 3） | manifest `tarBytes` |
| 发行包数 | 112 | manifest `dists` |
| Python / 平台 | 3.13 / linux_x86_64 | manifest |
| 关键 pin | torch 2.6.0+cu124、huggingface-hub 0.36.2、diffusers 0.32.2、onnxruntime-gpu 1.20.0、numba 0.68.0、numpy 2.5.3 | 构建 `IMPORT_OK` 与 manifest |
| wheelhouse 指纹 | `14f43fee…e3ad3` | 与仓库 `wheelhouse-manifest.json` 的 sha256 相同 |

归档用 `.tar.zst` 而不是 `.tar`：Kaggle 会在上传时展开普通归档，6.9 GB 的 site-packages 会变成几万个文件、超过 50 个顶层条目，bundling 实测拖到 45 min 仍未 ready（第一次发布的 `.tar` 因此没有出现）。`.tar.zst` 保持单文件，2.88 GB 上传后 4 min 内 ready；镜像自带 `zstandard` 0.25.0（2026-11-23 用 CPU 探针确认，`zstd` 二进制不存在），运行侧用 Python 流式解压，不依赖系统命令。

单归档是刻意的：数据集里 112 个 dist 展开是几万个文件，上传/挂载都更慢；单归档让 Kaggle 只处理一个对象，运行时按实际挂载形态决定是否解包。

## 运行侧协议

```
挂载 /kaggle/input/…/cosyvoice3-site-packages
  ├─ manifest.json        ← 与 git 的 site-packages-manifest.json 比对
  └─ site-packages.tar.zst ← 单文件、2.88 GB；或已解包/平铺的目录
        │
        ├─ dists 名/版本逐项相等？ tarBytes 相等？
        │     否 → 记一条日志，走原 wheelhouse 安装
        └─ 是 → python -S 子进程只带这个目录 import torch
               ├─ 失败 / torch.__file__ 不在目录内 → 回落
               └─ 通过 → sys.path.insert(0, target)，本次运行不执行任何 pip
```

- **校验在 import torch 之前**。生产内核原本在文件顶部就 `import torch`；fast path 必须在它之前完成，否则镜像的 torch 已经进 `sys.modules`，再挂目录也换不掉。
- **manifest 是 git 侧的记录**。Kaggle 的 `dataset_sources` 不能 pin 版本（`#521` 已实测：请求 `/3` 仍挂最新版），所以数据集重建后只能靠 `site-packages-manifest.json` 里的 dist 名/版本 + tar 大小发现漂移。单测 `tts-kaggle-site-packages.test.mjs` 会用合成 mount 真跑 `_site_packages_problems`，覆盖缺失发行包、版本变化、tar 字节变化、无 tar/无目录、空 manifest 五种拒绝路径。
- **回落不阻断出片**。挂载缺失、manifest 不符、解包失败、探针失败，四种情况都只打日志，然后继续原来的 wheelhouse 离线安装。
- **构建模式不要求 CUDA provider**。carrier 是 CPU 内核，`onnxruntime-gpu` 在 CPU 上只报 CPU provider；生产路径仍保留 `CUDAExecutionProvider` 硬断言。

## 边界与代价

1. **数据集不随 wheelhouse 自动更新。** wheelhouse 重建后，`site-packages-manifest.json` 的 `wheelhouseManifestSha256` 会对不上；单测会红，提醒重建数据集。运行侧则因 dist/版本/大小不符自动回落，不会静默用旧环境。
2. **首次挂载成本未知项已收敛。** 数据集挂载路径是 `/kaggle/input/datasets/xpabloli/cosyvoice3-site-packages`，里面只有 `manifest.json`（3,851 B）和 `site-packages.tar.zst`（2,879,940,507 B），Kaggle 不会把 zst 自动展开；内核必须解包到可写盘。GPU 首跑解包 50.7 s，CPU 探针 60.9 s；解包后 `/tmp` 多占 6.9 GB。
3. **数据集版本不可 pin。** 与 wheelhouse 同一个已知边界；manifest 只保证「挂到的就是我记录的」，不能保证「挂到的是我发布的那一版」。重建必须同步改 git。
4. **构建内核是 CPU。** 它只证明包能 import，不证明 CUDA provider；真正的 CUDA 证据仍由生产内核的 `CUDAExecutionProvider` 断言提供。
5. **磁盘。** 构建时 venv + tar 同时存在需要约 14 GB 工作盘；发布后数据集占 6.5 GB（tar 十进制 6.97 GB）。运行侧解包到 `/tmp` 需要额外 6.9 GB，P100/T4 容器够用，但同一容器跑其他大模型时要留意。

## 复现

```bash
# 1) 重建数据集（Kaggle 内构建、打包、发布）
scripts/short-video/kaggle/push-site-packages-build.sh

# 2) 把内核日志 SITE_PACKAGES_MANIFEST_BEGIN/END 之间的 JSON 写入
scripts/short-video/kaggle/site-packages-manifest.json

# 3) 真实冷启 + 重试验收（2 包 / 4 scene）
PACKS=baidu-token-market,deepseek-harness-desktop RETRY_COUNT=3 \
  PATH="/opt/homebrew/bin:$PATH" node scripts/short-video/kaggle/live-reuse-smoke.mjs
```
