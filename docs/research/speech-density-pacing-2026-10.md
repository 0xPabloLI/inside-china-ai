## 1. 基准：150 是「朗读带」，170-190 才是「信息播报带」

#235 采信的 140-160 wpm 来自「播音/播客/教学」语境——Teleprompter 类工具把 YouTube explainer 标在 130-160、有声书 150-160。而本管线做的是 60 秒信息型短视频：**单位时间要传达的事实密度接近新闻播报**，不是朗读。

Rodero 在 *Media Psychology*（2016）用 200 名受试、西语广播新闻片段做的识别实验给出了更贴合本场景的基准 [1][2]：

- 受试主观判定：**150 wpm = 慢，170-190 = 正常，210 = 快，230 = 认知过载**；
- 客观识别成绩：**170-190 区间最高，且与信息密度无关**；150（低密度）与 230（高密度）两组识别最差；
- 机制解释（「Moderate Dynamic Mechanism」）：语速决定可用于编码的认知资源，**速度越高，信息密度必须越低**；反之亦然。

这解释了一个此前被忽略的张力：150 并非「绝对偏慢」，而是**在低密度稿子上显得拖**——听众的注意力随动态性下降而流失。我们三个包的实测密度是 2.5-2.8 词/秒（150-168 wpm 等效），恰好落在「低速 + 中等密度」这个识别成绩偏差的象限。

Reynolds & Givens（2001，*Perceptual and Motor Skills*）把自然语音与合成语音放在 130/150/170/190 四档做句子验证任务 [3]：**语速对反应时没有显著主效应**（合成语音整体更慢，但那是音质代价，不是语速代价）。这条对我们是关键的安全边界——TTS 推到 170 不是「听得懂但跟不上」的区间。

实务侧的数字与学术侧同向但相互独立：TikTok/Reels 170-200、Shorts 170-200、新闻主播 180-200 [13][14]。它们多为工具站互引（同一段话反复转述），只能作为方向性佐证，不能当独立证据。

**结论**：把 EN 目标带从「140-160 甜点」改为「165-175 落地、上限 178」，落在 Rodero 的 170-190 下沿，同时给自动翻译观众（Tier 3 称短视频观众 60% 开自动翻译，有效阈值更低 [15]）留余量。

## 2. 停顿是独立杠杆，且是专业播报真正变快的地方

有效语速的分母是「发声时间 + 停顿时间」。同样 150 个词，停顿从 12% 压到 6%，WPM 就从 150 升到 160，而**音节一个都没加速**——听感上不「赶」，只是不拖。

语音学侧有两条硬证据：

- Castro 等（2010）实测巴西葡语 TV 新闻：6.0 音节/秒、**每分钟 19.8 次静音、平均 327ms、总停顿占 11%**，且无填充停顿 [5]；
- CBC 新闻 1937-1987 的纵向研究：**1966 年后停顿显著缩短、短语变长，而音节速率保持恒定**——专业播报的「变快」是编辑出来的，不是声带变快 [4]。

创作者侧的操作口径与此一致：删掉 >0.5s 的停顿、保留 0.1-0.2s 的呼吸垫、每 3-4 秒给一次画面变化 [6][7][8]。行业工具把它做成了默认能力（Descript 的「删除 0.5s 以上静音」），说明这不是玄学而是标准工序 [6]。

**对本管线的含义**：此前把「写稿密度」与「TTS 倍率」当两条杠杆，漏掉了第三条——**停顿裁剪**。它没有频谱代价（不改变音节），只改变时间轴，因此应当是提语速的第一顺位；倍率只在裁完停顿后仍不达标时补差。

可读出的三条：

- **只靠倍率**要到 170，需要 1.19-1.20×，且有 1-3 个场景触顶后仍停在 158-162——收益被 1.2 上限吃掉，频谱风险却全额支付；
- **只靠停顿**（150ms 地板）能到 167-171，零频谱代价，但 150ms 低于专业播报的 327ms 平均，听感可能「喘不上气」；
- **200-250ms 地板 + 165 目标**是满足「到 170 上下、最大倍率 ≤1.20、触顶 ≤1」的两组之一（另一组是 200ms/165：落点只高 1-2 wpm，但停顿更紧）。取 250ms 是风险优先——它比 200ms 少 50ms 的「抢拍」风险，而落点差异在测量噪声以内。

时长侧：三包 60 秒左右会缩到 55-57s（-4%~-6%），对完播率是方向性利好（完播率随时长单调下降），但会改变画面时长分配，属于实施阶段必须验证的风险点。

## 5. 机制缺口（本地源码 + 实证）

这两条是「慢」为什么一直没被闭环修掉的结构原因，也是 #279 无法只靠调常量解决的部分。

**5.1 生产引擎不裁停顿。** `cosyvoice3-kaggle-cuda.mjs` 的引擎描述里写死 `useSilenceFilter: false`（两处：引擎对象与 `postProcess()` 调用）[10]；而 ffmpeg 的 `silenceremove` 过滤器其实早已实现（`post-process.mjs`：`stop_periods=-1:stop_duration=0.25:stop_silence=0.08`）[9]。也就是说：**能力在、开关关着**。上面 10.5-13.7% 的停顿就是它关着的直接后果。

**5.2 hook floor 被缓存旁路。** `planTtsScenes()` 把命中的 approved 音轨直接归入 `cachedResults`，只有 pending/candidate 进入 `verifyScenes`；Quality Gate 与 `planPacingResponses()` 都只遍历 `verifyScenes` 的评估结果 [11]。结果是：**一条 1.0× 的 hook 一旦被批准进缓存，之后每次重跑都不会再被 #244 的 floor 抬起**。实证：v41-flash-1017 的 `scene-1.tts-meta.json` 记录 `ttsSpeed: 1`、实测 163 wpm，而该次运行日志写着 `TTS cache: 9/10 scenes reused` [12]。`SCENE_META_VERSION` 机制存在（用于语义变更时批量降级为 candidate 重验），但 floor 属于 pacing 语义、不在 gate 语义里，所以没有被它覆盖。

**含义**：#244 的「成品 hook 永远 ≥1.1」目前只是「本次新生成的 hook 永远 ≥1.1」。在讨论「floor 要不要抬到 1.15」之前，得先让 floor 对缓存命中的成品也生效——否则改数值只影响新生成的包。

> **2026-10-19 更新：#786 已关闭 5.1 与 5.2。** 5.1 换成 `silencedetect` 测量 + `aselect` 区间掩码（见 §6.1，`silenceremove` 无法表达「保住首尾」）；5.2 让缓存命中的 approved take 按 meta 时长复算 WPM 后进同一条补差梯子（`registry.mjs#planCachedPacing`），并在接受重生成 take 时丢弃对应 cache hit。

## 6. 实施验证（#786 交付实测，2026-10-19）

### 6.1 为什么不是 `silenceremove`

票面原本假设用 `silenceremove` 设下限，实测否决（ffmpeg 8.1.2，同一批真包）：

| 配置 | 结果 |
| --- | --- |
| `stop_periods=-1:stop_duration=0.25:stop_silence=0.08` | 尾部静音被一起裁掉（首尾必须保留） |
| `stop_silence=0.25` | 保留量语义：留下 0.349s，不是 0.25s 上限 |
| `stop_periods=1` | 只裁第一个停顿，尾部反而留着 |

改为**先测后切**：`silencedetect` 量出每个静音区间 → 计划 drop 区间 → `aselect='not(between(...)+...)'` + `asetpts=N/SR/TB`。首尾静音区间直接不进计划，样本逐位保留。

三个实现坑（都是真数据发现的，不是设计时想到的）：

1. **帧粒度**。`aselect` 按整个音频帧取舍，而 ffmpeg 8 把 44.1 kHz WAV 解码成 **4096 样本（93 ms）** 一帧，不是 1024。计划切在 225 ms 结果实测 271 ms（超上限）。修法：`aselect` 之前插 `asetnsamples=n=256:p=0`，粒度降到 ~5.8 ms。
2. **停顿被探测器拆开**。`silencedetect` 只要电平瞬间回到阈值之上就断开区间，一秒钟的停顿常被拆成 409 ms + 105 ms 两段；而 `d=0.15` 会把 <150 ms 的那段整个藏起来，于是计划只裁了前半截，实测 328 ms。修法：把测量下限降到 **100 ms** 并合并「间隔 ≤100 ms」的区间（100 ms 远短于最短的单词，长于爆破音闭塞，合并不吞语音）。
3. 合并 + 精度仍不能覆盖全部情况——停顿尾部是**下一词自己的渐入斜坡**，它比任何静态下限都可能更短。所以裁剪后**必须回测**：`verifySilenceFloor()` 量交付结果，超限就按实测重新计划再切一次（最多 2 轮）。`silent-update` scene 7 就是这样从 308 ms 修到 232 ms 的。

### 6.2b 产品验证门（implementation-workflow §9）

定性：**有产出差异（quality improvement）**。v41-flash-1017 用同一批真实音轨跑真实裁剪 + 真实补差规划，产出音频 58.08s → 54.55s（-6.1%），逐场景时长与停顿见上表；差异是**听得到的**（句子之间留白缩短、hook 实播 179 wpm），不是单测或 mock 层面的变化。未做的是「真机重生成 + 重渲染 MP4」：那需要 Kaggle GPU 段（see 6.4）。

### 6.3 对齐漂移校验（票内第一风险）

对 v41-flash-1017 的同一批 scene 分别对齐**原始音轨**与**裁剪后音轨**（`text-align.py` + `wav2vec2-large-960h-lv60-self`，CPU），比较逐词边界：

| 观察项 | 结果 |
| --- | --- |
| 词数 | 10 个场景全部一致（10/10 … 18/18），无丢词 |
| 首词起点 | 10 个场景全部相同（首部静音未动） |
| 变动 >50 ms 的词 | **每场恰好 1 个**，且都是被裁停顿的**前一个词**（对齐把停顿尾巴记在该词时长里，裁掉后它自然变短） |
| 其余词时长漂移 | ≤50 ms（wav2vec2 自身的对齐噪声量级） |
| 末词结束位移 | 等于该场裁掉的秒数（整条时间轴平移，不累积漂移） |

结论：字幕不会漂移，前提是**对齐跑在裁剪后的音轨上**。管线本来就满足（`postProcessBatch` 在 TTS 生成阶段就地裁剪，`runForcedAlignment` 之后才跑），且 `computeAlignmentSignature()` 把音频字节算进签名，旧 timing 会自动判 stale——不需要额外失效逻辑。

### 6.4 仍未验证

- **250 ms 是否「抢拍」**：离线测量不能替代耳朵，需真机 3 轮听审（165 / 170 / 175）。降级杠杆是 `TTS_SILENCE_FLOOR_MS`（250→300），它同时进 cache key，改数字即触发重生成。
- **真机产出一个包**：本节的 before/after 是「同一批真实音轨 + 真实裁剪 + 真实补差」的离线重跑，不是 GPU 重生成后的新包。差的只是 TTS 合成那一段（音色/随机性），裁剪与规划代码路径完全相同。
- **缓存失效的一次性 GPU 成本**：trim token 进了 scene key，旧 approved take 全部降级重生成。三包共 30 个场景，按 Kaggle 单场景耗时估算是一次性支出，未在本票实测。

## 反方观点与风险

- **体裁外推**：Rodero 的刺激是**西语广播新闻**，不是英文短视频。西语音节率更高，170-190 的「听感」不可直接搬到英语。但英文实操站点独立收敛到 170-200 [13][14]，方向一致——所以结论取「170 略保守」而非 190。
- **循环引证**：「TikTok 语速 170-200」这个数字在几十个工具站之间互相转述，找不到平台官方口径。本文把它降为 Tier 3 方向性佐证，主证据用 Rodero 与 Reynolds。
- **裁停顿可能「赶」**：150ms 地板低于专业播报 327ms 的平均停顿 [5]，连续短句场景会显得抢拍。建议从 250ms 起测，逐档下调。
- **密度耦合**：Rodero 明确「速度越高、密度必须越低」。如果同一轮既提密度又提速度，会双重挤压理解资源。本管线的密度预算是 ≤2.9 词/秒（≈175 wpm 等效），与 165-175 的目标并不冲突，但**不应同时把预算往 3.0 推**。
- **时间轴副作用**：音频变短会改变 ASS 字幕、ASR 对齐与场景时长分配。这是实施阶段的第一风险，不是研究能替它担保的部分。
- **自动翻译观众**：Tier 3 称 60% 短视频观众开自动翻译 [15]，该人群有效阈值更低——支持把上限压在 178 而不是 190。
- **口径提醒**：本文的 WPM 含停顿，与创作者「成片 wpm」可比；它不是音节速率，不能拿来和 6.0 syl/s 直接换算。
