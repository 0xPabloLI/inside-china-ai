## 1. Executive Summary

基于 15 个权威来源的深度调研（含 TikTok 官方 Creator Academy、TikTok Ads 官方博客、Reynolds Journalism Institute 新闻研究、Social Media Examiner、SocialKit、Darkroom 等），核心发现如下：

**2026 年短视频生态正在从「一次性爆款」转向「系列化/连续剧」模式。** TikTok 算法已从单纯奖励单条视频的完播率，进化到同时奖励 **episode-to-episode retention（集间留存）** 和 **sequential viewing（连续观看）**。当一个内容太丰富而无法在 60 秒内讲完时，拆分为多集系列**不是退而求其次，而是更优的算法策略**。

关键数据支撑：

- 57% 的消费者更偏好发布原创内容系列的品牌 [[8]](#13-来源清单)
- 系列内容的 save rate 是独立视频的 3 倍 [[8]](#13-来源清单)
- TikTok 官方推出 Growth Max for Mini Dramas，将连续剧内容作为平台级战略推广 [[6]](#13-来源清单)
- 2026 年需要 70%+ 完播率才能触发病毒式传播（2024 年只需 50%）[[3]](#13-来源清单)
- TikTok 算法自动把 Part 2 推给看过 Part 1 的观众 [[11]](#13-来源清单)

## 2. 为什么拆分多视频比强行压缩更好

### 2.1 算法逻辑

**SocialKit 的核心洞察** [[2]](#13-来源清单)：

> TikTok FYP 算法本质上是发现导向的——它擅长把内容推给新观众，但对留存是「冷漠的」。一条 20 万次冷启动观看带来的粉丝增长，约等于一条 5000 次温暖受众观看带来的增长。**连续剧内容改变这一动态**：
>
> 1. 它创造了关注理由——「我要看 Part 2」比「我喜欢这个账号」更容易转化
> 2. 它在账号层面产生留存——观众回到主页连续看多条，在旧内容上产生互动信号

**Medium 的算法分析** [[8]](#13-来源清单)：

> 完成 Part 1 的观众被算法视为强兴趣信号，**算法会主动把 Part 2 推给他们**，无需搜索。这意味着 Part 2 的冷启动比 Part 1 更容易。

**Darkroom 2026 算法分析** [[11]](#13-来源清单)：

> "Publish parts (Part 1/2/3). TikTok often recommends episode 2 to viewers of episode 1 — this drives session depth and follows."

### 2.2 完播率优势

**Socialync 的完播率数据** [[3]](#13-来源清单)：

| 视频时长 | 达到 70% 完播需观众至少看 | 难度   |
| -------- | ------------------------- | ------ |
| 15 秒    | 10.5 秒                   | 最容易 |
| 30 秒    | 21 秒                     | 适中   |
| 60 秒    | 42 秒                     | 很难   |

> 一条 15 秒视频 100% 完播，**永远**打败一条 60 秒视频只看一半的。

**推论**：如果内容需要 120 秒才能讲完，拆成 2×60 秒不如拆成 4×30 秒——后者每条都更容易达到 70% 完播率门槛。

### 2.3 系列内容的复合效应

- **Short Video SEO (SVSEO)**：每集都是一个新的关键词触点，在 TikTok 搜索中被索引，形成复利式有机发现 [[8]](#13-来源清单)
- **沉没成本效应**：看了 3 集的观众比看了 1 条独立视频的观众投入更多注意力，更倾向于继续追完 [[2]](#13-来源清单)
- **主页访问信号**：系列观众回到主页按顺序看，在旧内容上产生互动信号，这会提升算法对未来内容的待遇 [[2]](#13-来源清单)
- **Rewatch rate > 粉丝数**：2026 年 TikTok 算法中，rewatch/loop rate 已超越粉丝数成为核心排名信号 [[11]](#13-来源清单)

## 3. 内容拆分策略：如何把一篇文章拆成多集

### 3.1 拆分决策树

```
文章总信息量评估
├── 能在 60 秒内讲完核心叙事？
│   └── YES → 单条视频（当前管线）
│   └── NO → 评估拆分
│       ├── 有 2-3 个独立的子话题？
│       │   └── YES → 主题拆分（每集讲一个子话题）
│       │       例如：DeepSeek 蒸馏风波
│       │       Part 1: 事件起因（OpenAI 数据指控）
│       │       Part 2: 各方回应（DeepSeek、字节、阿里）
│       │       Part 3: 行业影响与未来走向
│       └── 是一条因果链但太长？
│           └── YES → 叙事拆分（按因果链断点）
│               例如：华为 AI 芯片突破
│               Part 1: Hook + 背景（为什么重要）
│               Part 2: 技术突破点
│               Part 3: 对产业链的影响
```

### 3.2 拆分原则

| 原则                            | 说明                                                                                         | 来源                |
| ------------------------------- | -------------------------------------------------------------------------------------------- | ------------------- |
| **每集独立可看**                | Part 3 的观众可能没看过 Part 1，每集必须有独立的 Hook 和价值主张                             | [[2]](#13-来源清单) |
| **Part 1 结构性不完整**         | Part 1 应该让观众在 20 秒内意识到「这条视频不看完 Part 2 就不完整」                          | [[8]](#13-来源清单) |
| **信息间隔（Information Gap）** | 在一集提出问题/悬念，在下一集解答——创造心理上的「未闭合环」                                  | [[2]](#13-来源清单) |
| **奖励强化**                    | 每集的 payoff 必须兑现承诺——如果 Part 2 令人失望，整个系列的信任链断裂                       | [[2]](#13-来源清单) |
| **Part 2 Hook 双重功能**        | 「如果你看过 Part 1，你知道 [上下文]——接下来发生的事更精彩」既奖励老观众，又给新观众足够背景 | [[2]](#13-来源清单) |
| **最多 3-5 集**                 | 超过 5 集观众流失率显著上升；如果内容更多，拆成多个独立系列                                  | [[2]](#13-来源清单) |

### 3.3 适合 China AI News 的系列类型

基于 SocialKit 的系列分类表和 Reynolds Journalism Institute 的新闻 TikTok 研究 [[7]](#13-来源清单)：

| 系列类型               | 适用场景                     | 长度   | 示例                                |
| ---------------------- | ---------------------------- | ------ | ----------------------------------- |
| **Explicit Part N**    | 复杂事件分析（多因果链）     | 2-3 集 | DeepSeek 蒸馏风波（起因/回应/影响） |
| **Loop-and-Flashback** | 突发新闻（先给结果再补背景） | 1-2 集 | 某公司被制裁→背景解释               |
| **Deep Dive**          | 技术深度解析                 | 2-4 集 | 华为芯片技术拆解（每集一个技术点）  |
| **对比系列**           | 多公司/多产品对比            | 2-3 集 | DeepSeek vs Qwen vs GLM 定价对比    |

## 4. 每集的结构设计

### 4.1 单集内部结构（基于 Socialync 的完播率研究 [[3]](#13-来源清单)）

针对 60 秒的 TikTok 视频：

```
0-3s:   Hook — 直接给 payoff，不要 setup
3-10s:  问题/背景 — 快速建立上下文
10-45s: 核心内容 — 按 3-5 秒一个 pattern interrupt 节奏
45-55s: 高潮/关键数据
55-60s: 系列钩子 — "Part 2 会告诉你 [更重要的东西]" + CTA
```

### 4.2 Rewatch 机制设计（来自 Darkroom [[11]](#13-来源清单)）

每集应设计至少一个 rewatch 触发点：

| 机制         | 做法                                   | 效果         |
| ------------ | -------------------------------------- | ------------ |
| **隐藏细节** | 画面中放一个观众第一遍可能错过的细节   | 重看寻找细节 |
| **循环揭示** | 结尾视觉上连接开头，形成无缝循环       | 自然 rewatch |
| **问题反转** | 结尾抛出一个让开头产生新含义的问题     | 重新理解开头 |
| **视觉谜题** | 画面中有一个需要重看才能解开的视觉谜题 | 主动重看     |

### 4.3 系列间连接策略

| 策略                    | 具体做法                                                                                                 | 来源                |
| ----------------------- | -------------------------------------------------------------------------------------------------------- | ------------------- |
| **Pin Part 1**          | 将系列的第一集 pin 在主页顶部                                                                            | [[2]](#13-来源清单) |
| **Stitch 自身视频**     | Part 2 开头 Stitch Part 1 作为「上集回顾」，既给老观众回顾，又给新观众上下文，同时告诉算法两条视频有关联 | [[2]](#13-来源清单) |
| **Pinned Comment 链接** | 每集的第一条评论放上一集链接 + 上下文提示                                                                | [[1]](#13-来源清单) |
| **视觉一致性**          | 系列内保持一致的视觉风格（颜色、字幕格式、logo 位置），但每集有不同的核心数字/画面                       | [[1]](#13-来源清单) |
| **Part 编号**           | 画面上明确标注 "Part 1/3" 等                                                                             | [[1]](#13-来源清单) |

## 5. 集间串联机制

### 5.1 平台内建工具

| 工具                 | 资格要求        | 功能                                                 | 来源                 |
| -------------------- | --------------- | ---------------------------------------------------- | -------------------- |
| **TikTok Playlist**  | ≥10,000 粉丝    | 在主页把视频分组排序，观众可以按顺序观看             | [[10]](#13-来源清单) |
| **TikTok Series**    | 企业/创作者账号 | 付费或免费的系列集合，观众在一个页面内连续看完所有集 | [[5]](#13-来源清单)  |
| **YouTube Playlist** | 所有账号        | 把 Shorts 或长视频组织成播放列表                     | [[14]](#13-来源清单) |

### 5.2 不依赖 Playlist 的串联方法（适合 <10K 粉丝账号）

| 方法                      | 具体操作                                                                                             | 算法效果                             |
| ------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------ |
| **Pin Part 1 到主页顶部** | 每次发新集时，确保 Part 1 始终是 pinned video                                                        | 新观众从 Part 1 开始追               |
| **Pinned Comment 互链**   | Part 2 的 pinned comment 写「Part 1 链接：[URL]」；Part 1 的 pinned comment 写「Part 2 已出：[URL]」 | 算法权重信号 + 导航                  |
| **Stitch 自己的视频**     | Part 2 开头用 Stitch 功能引用 Part 1 的片段作为「上集回顾」                                          | 告诉算法两条视频有关联；触发集间推荐 |
| **统一 Hashtag**          | 所有集用同一个专属 hashtag，如 `#deepseekdistillation`                                               | 搜索时按 hashtag 聚合                |
| **Caption 标注**          | 每条 caption 写「Part X/Y · [系列名]」                                                               | 搜索可发现                           |

### 5.3 算法自动串联（关键发现）

**Darkroom 2026 算法分析** [[11]](#13-来源清单)：

> "TikTok often recommends episode 2 to viewers of episode 1 — this drives session depth and follows."

算法的集间推荐机制：

1. 观众看完 Part 1 → 算法记录「对这个内容有强兴趣」
2. Part 2 发布时 → 算法优先推给这些「高兴趣」观众
3. 这些观众的 Part 2 完播率通常更高（已有上下文）→ 算法进一步扩大推荐

## 6. 叙事连贯技巧

### 6.1 叙事连贯

| 层面                            | 具体技巧                                            | 示例                                                                                               |
| ------------------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **信息间隔（Information Gap）** | Part 1 提出问题，Part 2 解答，Part 3 给出更深的影响 | Part 1: "OpenAI 指控 DeepSeek 蒸馏" → Part 2: "DeepSeek 怎么回应的" → Part 3: "这对行业意味着什么" |
| **叙事回调**                    | Part 2+ 开头回顾 Part 1 的关键点，但用不同角度      | "如果你看了 Part 1，你知道 OpenAI 的指控——但 DeepSeek 的回应让所有人都意外了"                      |
| **因果链推进**                  | 每集结尾引入新的因果环节                            | Part 1 结尾: "但真正的争议不在于数据，而在于一个更深的问题..." → Part 2 解答                       |
| **沉没成本承诺**                | 每集的 payoff 兑现承诺，让观众觉得「追下去值得」    | 如果 Part 2 令人失望，整个系列的信任链断裂                                                         |

### 6.2 视觉连贯

| 元素          | 连贯做法                                                   |
| ------------- | ---------------------------------------------------------- |
| **配色方案**  | 系列内所有集用同一套品牌色板（如 cyber dark + amber）      |
| **字幕格式**  | 系列内字幕大小、位置、背景色一致                           |
| **Logo 位置** | 所有集 logo 在相同位置（55px, bottom right, opacity 0.18） |
| **画面编号**  | 每集画面明确标注 "Part X/Y"                                |
| **场景模板**  | 系列内复用相同的 scene templates（hook → data → CTA）      |

### 6.3 连贯的「红线」

| 避免                                          | 原因                         | 正确做法                          |
| --------------------------------------------- | ---------------------------- | --------------------------------- |
| Part 3 必须看 Part 1 才能看懂                 | FYP 新观众直接划走           | 每集独立可看，系列只是 bonus      |
| 所有集用完全相同的 Hook                       | 老观众无聊                   | 每集不同角度的 Hook               |
| Part 1 用 hard cliffhanger 但 Part 2 令人失望 | 训练观众「你的悬念不值得追」 | 慎用 cliffhanger，payoff 必须兑现 |
| 系列间隔超过 1 周                             | 观众心理上已关闭这个系列     | 1-3 天内发完                      |

## 7. 用户发现机制

### 7.1 TikTok 内发现路径

```
发现路径 1: FYP 推荐（主路径）
  └── 算法 test-and-expand 循环
      ├── 微观众测试（基于 sound, hashtag, 兴趣推断）
      ├── 早期信号（完播率 > rewatch > 分享 > 评论 > 关注）
      └── 扩大到更多兴趣聚类

发现路径 2: TikTok Search（新兴路径）
  └── 用户主动搜索关键词
      ├── caption 中的关键词被索引
      ├── 画面文字被转录
      └── 每集是独立的搜索触点 → 系列形成搜索复利

发现路径 3: 算法集间推荐（系列专属）
  └── 看过 Part 1 的人自动收到 Part 2 推荐
      └── 基于集间留存信号 (episode-to-episode retention)
```

### 7.2 发现优化策略

| 策略                             | 具体做法                                                                                  | 来源                 |
| -------------------------------- | ----------------------------------------------------------------------------------------- | -------------------- |
| **Answer-First Scripting (AEO)** | 先用一句话回答问题，再展开论证。TikTok AI 助手层会把清晰回答的视频作为「答案」直接展示    | [[11]](#13-来源清单) |
| **Caption 做微博客**             | caption = 关键词 + 利益点 + CTA + 2-3 个精准 hashtag                                      | [[11]](#13-来源清单) |
| **SVSEO 复利**                   | 每集 caption 和画面文字围绕系列核心关键词优化。新集发布 = 新搜索触点                      | [[8]](#13-来源清单)  |
| **First-Hour Engagement Sprint** | 发布后第一小时快速回复评论、种草问题引导讨论线程。早期有意义的互动信号触发算法扩大推荐    | [[11]](#13-来源清单) |
| **Loopable Edits**               | 结尾视觉上连接开头，或留下需要重看才能发现的细节。Rewatch rate 是 2026 年最重要的算法信号 | [[11]](#13-来源清单) |
| **Niche + Rising Sounds**        | 选择正在上升的、与你的领域匹配的音频，而非大众病毒音频                                    | [[11]](#13-来源清单) |

### 7.3 跨平台发现

| 平台                       | 发现方式             | 合集策略                           |
| -------------------------- | -------------------- | ---------------------------------- |
| **YouTube Shorts**         | 算法推荐 + 搜索      | 可创建 Playlist 把所有集组织在一起 |
| **YouTube 长视频（合集）** | 搜索 SEO + 推荐      | 把所有集合并为一个长视频发布       |
| **网站文章**               | SEO + 直接访问       | 文章内嵌视频，系列文章互链         |
| **Publora 跨平台发布**     | 一次性发布到所有平台 | 系列统一 hashtag 跨平台追踪        |

## 8. 合集制作

### 8.1 什么是合集？

合集 = 把多集短视频合并为一条长视频，发布在不同平台。不是简单首尾相接——需要重新设计叙事节奏。

### 8.2 合集的三种形态

| 形态            | 时长      | 平台           | 内容                                                         | 来源                 |
| --------------- | --------- | -------------- | ------------------------------------------------------------ | -------------------- |
| **A. 原始拼接** | 2-4 分钟  | YouTube 长视频 | 直接把 Part 1-3 首尾相接，加简单转场                         | [[12]](#13-来源清单) |
| **B. 重构叙事** | 3-5 分钟  | YouTube 长视频 | 去掉每集的 Hook/CTA，重新组织为一条连贯长叙事                | [[13]](#13-来源清单) |
| **C. 深度扩展** | 5-10 分钟 | YouTube 长视频 | 在合集基础上加入 Part 1-3 中没讲的细节、更多数据、更深层分析 | 原创策略             |

### 8.3 合集的好处

**SendShort 和 HeyGen 的分析** [[12]](#13-来源清单) [[13]](#13-来源清单)：

1. **触达更广受众** — YouTube 观众可能不在 TikTok 上
2. **最大化内容价值** — 同一素材在 TikTok（短视频）和 YouTube（长视频）各发一次
3. **更好的参与度** — 短片段拼接的长视频通常观看时长更高
4. **吸引新订阅** — 喜欢合集的观众可能订阅频道
5. **内容货币化** — YouTube 长视频可以广告变现

### 8.4 合集发布时机

```
Day 1: 发布 Part 1 (TikTok + YouTube Shorts)
Day 2: 发布 Part 2 (TikTok + YouTube Shorts)
Day 3: 发布 Part 3 (TikTok + YouTube Shorts)
Day 7: 发布合集 (YouTube 长视频) + 网站文章更新
```

> 合集在所有集发完 3-5 天后发布，这样：
>
> - TikTok 系列的热度还在
> - 合集给追了系列但想要完整版的观众一个归宿
> - YouTube 长视频的 SEO 开始积累
> - 没追到系列的新观众通过 YouTube 搜索发现合集

### 8.5 对我们管线的建议

我们有独特优势——**已经有原始文章和 scene-data，所以合集可以自动生成**：

```
方案 A（自动拼接）— 技术最简单：
  FFmpeg concat 拼接 + 交叉淡入淡出

方案 B（重构叙事）— 效果更好：
  Agent 重新编排 voiceover，去掉每集 Hook/CTA，
  生成新的 scene-data → TTS → 渲染 → 合成
```

## 9. 自动分集评估器（管线集成）

> **此章节为管线集成设计**。Agent 在 Stage 3（文章 → scene-data）执行此评估器，自动判断是否需要拆分，给出推荐集数和理由。

### 9.1 评估器输入

```
输入：
  - 文章全文（frontmatter + markdown body）
  - 文章章节数
  - 每章节字数
  - 关键数据点数量
  - 关键人物/公司数量
  - 因果链深度
```

### 9.2 评估器逻辑

```pseudo
STEP 1: 估算单条视频时长
  voiceover_word_count = 提取文章核心叙事的字数
  estimated_duration = voiceover_word_count / 2.5  // F5-TTS 平均 2.5 词/秒

STEP 2: 判断是否需要拆分
  IF estimated_duration <= 60s:
    → 单条视频（推荐集数 = 1）
    → 理由：核心叙事可在 60 秒内讲完，无需拆分

  ELSE IF estimated_duration <= 120s:
    → 评估内容结构
    IF 文章有 2-3 个独立子话题:
      → 拆 2 集（推荐集数 = 2）
      → 理由：内容超出 60 秒，且存在 [N] 个独立子话题，适合主题拆分
    ELSE:
      → 拆 2 集（推荐集数 = 2）
      → 理由：内容超出 60 秒，按因果链断点拆分为 2 集

  ELSE IF estimated_duration <= 180s:
    IF 文章有 3 个独立子话题:
      → 拆 3 集（推荐集数 = 3）
      → 理由：内容需 [X] 秒，存在 3 个独立子话题，适合 3 集主题拆分
    ELSE:
      → 拆 3 集（推荐集数 = 3）
      → 理由：内容需 [X] 秒，按因果链拆分为 3 段

  ELSE IF estimated_duration <= 240s:
    → 拆 4 集（推荐集数 = 4）
    → 理由：内容需 [X] 秒，拆为 4 集保证每集 ≤60 秒

  ELSE:
    → 拆 5 集（推荐集数 = 5，上限）
    → 理由：内容非常丰富，需 [X] 秒。建议拆为 5 集（上限），
            如内容更多，考虑拆为两个独立系列

STEP 3: 确定拆分方式
  IF 文章章节有明确的主题边界:
    → 主题拆分（每集讲一个子话题）
  ELSE:
    → 叙事拆分（按因果链断点）

STEP 4: 为每集设计
  - 独立 Hook（不同角度）
  - 系列连接钩子（cliffhanger / 叙事回调）
  - Rewatch 机制
  - Part 编号标注
```

### 9.3 评估器输出格式

Agent 在 HITL-2 审阅时输出如下结构：

```
📊 分集评估报告
━━━━━━━━━━━━━━━━━━━━━━━━
文章：[标题]
估算单条时长：[X] 秒
推荐集数：[N] 集
拆分方式：[主题拆分 / 叙事拆分]
━━━━━━━━━━━━━━━━━━━━━━━━
理由：
1. [主要理由]
2. [次要理由]
3. [次要理由]
━━━━━━━━━━━━━━━━━━━━━━━━
各集概览：

| 集 | 标题 | 核心内容 | Hook 类型 | 时长(估) |
|----|------|---------|----------|----------|
| 1  | ... | ... | ... | ... |
| 2  | ... | ... | ... | ... |
| ... | ... | ... | ... | ... |

━━━━━━━━━━━━━━━━━━━━━━━━
合集计划：
- 合集形态：[A拼接 / B重构]
- 合集时长(估)：[X] 分钟
- 合集发布时间：所有集发完后 3-5 天
━━━━━━━━━━━━━━━━━━━━━━━━
```

### 9.4 评估器的判断维度

| 维度               | 测量方法                   | 拆分阈值                        |
| ------------------ | -------------------------- | ------------------------------- |
| **叙事时长**       | 核心叙事字数 ÷ 2.5 词/秒   | >60s 触发拆分                   |
| **子话题数量**     | 文章章节的独立主题数       | ≥2 个 → 主题拆分                |
| **因果链深度**     | 事件之间的逻辑链层数       | ≥3 层 → 叙事拆分                |
| **数据点密度**     | 关键数字/引用/对比的数量   | >8 个 → 考虑拆分（每集 3-4 个） |
| **人物/公司数**    | 涉及的独立实体数量         | >4 个 → 考虑拆分（每集 ≤3 个）  |
| **信息类型多样性** | 数据/引用/对比/时间线/分析 | ≥3 种 → 适合拆分                |

### 9.5 评估器在管线中的位置

```
Stage 3: 文章 → scene-data
  ├── Step 0: 运行分集评估器 ← 新增
  │   ├── 输出推荐集数 + 理由
  │   ├── 输出各集概览
  │   ├── 输出合集计划
  │   └── 等待用户确认（如拆分）
  ├── Step 1: 生成 N 份 scene-data（如拆分）
  │   └── 每份含 seriesMeta 字段
  ├── Step 2: 设计集间连接
  │   ├── 每集的 Hook（不同角度）
  │   ├── 每集的系列连接钩子
  │   └── 每集的 rewatch 机制
  └── Step 3: 输出合集版 scene-data 草稿
```

## 10. 发布策略

### 10.1 发布节奏

| 策略             | 推荐间隔     | 理由                                              | 来源                |
| ---------------- | ------------ | ------------------------------------------------- | ------------------- |
| **快速连续发布** | 1-3 天       | 保持「未闭合环」的张力；超过 1 周观众会忘记上下文 | [[2]](#13-来源清单) |
| **同日发布**     | 同日不同时段 | 适合 2 集系列；Part 1 上午发，Part 2 下午发       | [[1]](#13-来源清单) |
| **间隔太长**     | >1 周        | ❌ 观众心理上已「关闭」这个系列                   | [[2]](#13-来源清单) |

### 10.2 平台适配

| 平台                       | 系列适配                                                 | 操作           |
| -------------------------- | -------------------------------------------------------- | -------------- |
| **TikTok**                 | 每集独立发布，60-70s；利用 Playlist 分组（需 ≥10K 粉丝） | 当前管线已支持 |
| **YouTube Shorts**         | 同一集可延长到 170s（完整版），TikTok 用精简版           | 当前管线已支持 |
| **YouTube 长视频（合集）** | 所有集合并为一个 2-5 分钟长视频                          | 新增脚本       |
| **Instagram Reels**        | ≤90s                                                     | 当前管线已支持 |

### 10.3 批量生产

**Medium 的批量制作模型** [[8]](#13-来源清单)：

> 一个 10 集系列可以在一天内拍完：统一场景设置、连续拍摄、下午粗剪审核。
> 相比每天做一条独立视频，批量制作系列可以 **减少 60-70% 的单条制作时间**。

**适配我们的管线**：一篇文章如果决定拆成 3 集系列，可以在 Stage 3 一次性写出 3 份 scene-data，然后批量跑 TTS → 渲染 → 合成。

## 11. 常见错误

| 错误                                | 后果                         | 正确做法                               | 来源                |
| ----------------------------------- | ---------------------------- | -------------------------------------- | ------------------- |
| Part 3 不看 Part 1 就看不懂         | FYP 新观众直接划走           | 每集独立可看，系列只是 bonus           | [[2]](#13-来源清单) |
| 系列间隔太长                        | 观众忘了上下文，追番意愿消失 | 1-3 天内发完                           | [[2]](#13-来源清单) |
| Hard cliffhanger 但 Part 2 令人失望 | 训练观众「你的悬念不值得追」 | 慎用 hard cliffhanger，payoff 必须兑现 | [[2]](#13-来源清单) |
| 把 60 秒硬塞成 120 秒               | 完播率 < 50%，算法不推       | 拆短，宁可少讲也不要拖                 | [[3]](#13-来源清单) |
| 所有集用同一个 Hook                 | 老观众无聊，新观众无法区分   | 每集不同角度的 Hook                    | [[1]](#13-来源清单) |
| 系列超过 5 集                       | 后半段观看量断崖式下跌       | 2-3 集最佳，最多 5 集                  | [[2]](#13-来源清单) |

## 12. 管线改进建议

### 12.1 Stage 3 增加「拆分评估」步骤

在文章 → scene-data 转换时，Agent 先运行分集评估器（见第 9 章），输出推荐集数和理由，等待用户确认。

### 12.2 scene-data 格式扩展

每份 scene-data 增加 `seriesMeta` 字段：

```javascript
seriesMeta: {
  seriesId: "deepseek-distillation",      // 系列唯一标识
  partNumber: 1,                           // 第几集
  totalParts: 3,                           // 总集数
  prevPartSlug: null,                      // 上一集 slug
  nextPartSlug: "deepseek-distillation-pt2", // 下一集 slug
  hookType: "standalone",                  // standalone | recap | cliffhanger-close
  rewatchElement: "hidden-detail",         // 本集的 rewatch 机制
  compilationSlug: "deepseek-distillation-full", // 合集 slug
  compilationSkipScenes: ["hook-scene-1", "cta-scene-final"], // 合集版跳过的 scene
}
```

### 12.3 发布脚本扩展

- `publish-tiktok.mjs`：发布 Part N 时自动在 caption 加入系列 hashtag；Pinned comment 加入上一集链接
- `publish-youtube.mjs`（新增）：合集版 mp4 发布到 YouTube 长视频

### 12.4 HITL-2 审阅扩展

当拆分为多集时，HITL-2 审阅增加：

- 系列整体叙事是否通顺
- 每集是否独立可看
- 集间连接钩子是否有效
- 拆分是否合理（有没有应该合并的集）
- 合集计划是否合理

### 12.5 新增 Stage 5.5: 合集制作

```
Stage 5 (TikTok 发布) 完成后
  → 等待 3-5 天
  → Stage 5.5: 合集制作
      ├── 方案 A: FFmpeg 自动拼接（快速，适合 2 集）
      ├── 方案 B: 重构叙事（效果好，适合 3+ 集）
      → 输出合集 mp4
      → 发布到 YouTube 长视频
      → 网站文章更新嵌入合集视频
```
