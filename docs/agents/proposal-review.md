# Proposal Review

> 给出代码、架构、工具、服务、模型或流程修改建议前执行。目标是让建议可追溯、影响面完整，并区分事实与推断。

## 1. 因果依据

每个“A 导致 B”的判断必须有可追溯证据，例如代码行、运行日志、Analytics、测试、spec 或官方文档。单一相关数据点不能直接推出代码层根因。

效果数据显示现状不佳时，应重新审视旧设计决策；同样，优化建议也必须说明作用机制和验证方法。

## 2. 影响面

提出改动前搜索：

- 定义与所有调用方；
- 测试与 fixtures；
- 文档、ADR、spec 和 issue；
- 跨 step 生产者与消费者；
- 同一契约在其他语言、CLI、runtime 或部署路径中的实现。

列出 Modified Files Impact，并说明现有行为、下游消费者、最坏后果和验证方式。不能把未搜索到证据表述为“不受影响”。

## 3. 事实双源

影响设计选择的外部事实至少用两个独立来源验证。优先级：

1. 本地安装版本、源码、CLI `--help` 和最小 smoke test；
2. 官方文档、官方仓库、release 或定价页；
3. 网络讨论仅证明“有人报告过”，不能证明当前版本仍存在或已经修复。

冲突时，以当前本地源码和实际调用结果为准，并记录版本差异。

工具或 CLI 是否存在时，使用本地可执行性检查加官方文档。定价、费率、资源分配等数值必须以官方定价页或官方 CLI 为准。

具体操作程序（源码验证链、CLI 确认命令、定价查询、维护状态检查步骤）见 `docs/conventions/fact-verification.md`。

## 4. 新工具准入

推荐引入新工具、框架或服务前检查：

- 官方仓库是否 archived；
- 最近 commit 与 release 日期；
- open/closed issue 活跃度；
- license、商业使用限制和安全边界；
- 与现有工具重叠度；
- 最小本地 smoke test；
- 官方仓库已 archived 或最近 commit 超过 6 个月的项目，不推荐引入。若存在活跃 fork 或新 maintainer，将其作为独立候选重新完成本节检查，而不是把计划中的维护当作豁免。

工具发现和完整评估流程见 `docs/tools-catalog.md`。

## 5. AI 模型参数

每个模型的推理参数从该模型自己的 README 或 Model Card 官方示例开始，不跨模型复制 steps、CFG、cache、offload 或持久参数设置。

在建议参数前：

1. 确认本地 package 和模型版本；
2. 读源码默认值与条件分支；
3. 验证一个参数是否会被另一个默认值覆盖；
4. 先跑官方基线，再做单变量优化；
5. 记录质量、速度、内存和硬件环境。

模型来源、许可与 Apple Silicon 准入规则见 `docs/research/model-sources-reference.md`。

## 6. 输出检查

建议至少包含：

- 已验证事实；
- 仍属假设的部分；
- 推荐方案与被否决替代方案；
- 修改影响面；
- 验证计划；
- 未解决风险。
